# 测量方法与踩过的坑

这份文档的价值不在方法本身，而在**哪些数字可信、为什么**。下面每一个缺陷都真实发生过，
且每一个都**静默**产生过错误数据。

---

## 1. 公平性契约

同一个进程里同时注册 `/sse/stream` 和 `/ws/stream`，两者共用：

| 共用 | 在哪 |
|---|---|
| 帧字节 | `Frame` 每 tick 每 room **只序列化一次**，两边拿同一对象 |
| 连接规则 | `Session`：有界队列 256、每连接一个虚拟线程的阻塞写循环、队列满即关、15s 心跳 |
| 注册表与扇出 | `Registry` + `TickPublisher`，单条平台线程 compose 并 enqueue |
| 容器限额与 JVM 参数 | `--cpus 4 --memory 8g`，同样的 `JAVA_OPTS` |

**唯一的变量是 wire framing。** 用两个进程对比会各自带来自己的堆、GC 和容器，任何差异都可能来自那些东西。

跨语言实现（Go / Rust）复制同样的语义：265 字节帧、1 Hz、每 room 一次序列化、256 深有界队列、满则关连接。

## 2. 指标选择 —— 三次选错的教训

| 指标 | 什么时候能用 | 什么时候不能用 |
|---|---|---|
| `heapUsedMb` | **基本不能用** | 含浮动垃圾。堆上限 5.6 GB 时 G1 没理由回收，2000 连接读到 286 MB，折算出的「143 KB/连接」几乎全是垃圾 |
| `heapLiveMb` | JVM **内部**对比 | ① 跨语言无意义（Go 的 `HeapAlloc` 语义不同，Rust 无 GC）② 测不出分配率——分配热点产生的是垃圾，垃圾被回收掉不进存活集 |
| `rssMb` | **跨运行时唯一的共同货币**；cgroup 真正据以杀进程的数 | 含线程栈、metaspace、直接缓冲，与 `heapLive` 排序可能不同 |

⚠ **换口径会改变排序**：按存活堆 Jetty(17.6 KB) 胜过 Netty(19.5 KB)；按 RSS 则 Netty(36 KB) 明显胜过
Jetty(64 KB)。**两张表不能混着读。**

⚠ **每连接成本必须用斜率，不能用单点减基线**：各栈空载基线差异巨大（Tomcat 74 MB / Jetty 19 MB /
Netty 16.9 MB / Go 6.6 MB / Rust 1.1 MB 的 heapLive，RSS 则是 294 / 272 / 263 / 6.6 / 1.1 MB）。
用同一个截距会把结论算废。

## 3. 直方图

服务端与客户端共用同一套桶：线性到 8 µs，之后**每倍程 4 个子桶**，最坏误差 25%。

**分辨率是刻意的**：两个 transport 预期差异是几十个百分点而非几倍；普通的倍增桶会把它们放进同一个桶
并报告为「完全相同」——那是一个看起来很干净的错误答案。共用桶还让两个直方图可以相减，
从而判断 p99 是落在服务端还是网络上。

⚠ 直方图**累计整个 run，包含 ramp 阶段**，不是纯稳态值。ramp 占样本比例小（10–20s vs 90s hold），
方向上偏悲观。

## 4. harness 自身的十个缺陷（十个都已修，最后四个是本轮补的）

### 缺陷 1 · 并发编排互删容器
所有 `run.sh` 共用固定容器名，且启动时 `docker rm -f` 它们。同时排三条后台链 → 互删对方容器。
**失败静默**：`docker wait` 成功、`docker logs` 报 "No such container"、`set -e` 退出、
结果目录只剩空日志。
**已修**：原子 `mkdir /tmp/ssebench.lock`，`profile.sh` 也纳入 —— 它容器名不同不会报错，
但会抢同一台机器的 CPU，**两边数据一起变错比报错更糟**。
这把锁曾经只守得住启动那几毫秒（run 主体不持锁）—— 见缺陷 7，本轮已修，实现挪到 `bench/benchlock.sh`。

### 缺陷 2 · 字符串替换静默失败
给 `run.sh` 加 CPU 峰值显示的补丁目标串没匹配上，`.replace()` 什么都没做，而只验了 `bash -n` 语法。
后果：此后每次手算 CPU，**而这道防线本该第一时间喊出「客户端饱和，此 run 作废」**。
**已修**：每次替换后逐标记验证。

### 缺陷 3 · 无超时的等待循环
`profile.sh` 死等 `liveSessions = CONNS`；客户端饱和达不到目标就正常退出了，脚本却在等一个
永不会到来的数字，**堵塞队列 20 分钟、零产出**。
**已修**：deadline + 客户端存活检查。

### 缺陷 4 · 压测端饱和使三个 p99 作废
h2 spc=1@20k（406%/400%）、spc=3@20k（399%/400%）、h2@40k（190%/200%）。
**服务端读数看着很从容**（335%/400%），只看服务端会误判成服务端到顶。
内存数字不受影响——连接建起来内存就占住了。
**已修**：每次 run 自动打印各容器 CPU 峰值。

### 缺陷 5 · 按行位置提取服务端快照
`run.sh` 用 `tail -n 3 | head -n 1`，**假设每条样本一行**。Go 的 stats 接口用
`json.NewEncoder().Encode()`，它补一个 JVM actuator 不补的换行——样本变两行，启发式取到空行，
`summary.json` 里服务端字段**全部为 null**。
**已修**：按内容匹配最后一条满载样本。**跨四种运行时的 harness 不该假设它们的 JSON 序列化器行为一致。**

### 缺陷 6 · 把拆连接的瞬间当成 hold 读数
缺陷 5 的修法（"取最后一条 `liveSessions` 非零的样本"）**假设非零就等于还在承载负载**。
服务端自己的计数器比内核慢一整条样本：压测容器被拆掉时 socket 已经关了、RSS 已经掉下去了，
它还在报满员，而且 `disconnects` 记的是 0。Rust @ 100,000 照着这条样本发布了 **228.8 MB**，
而平台稳态是 **3389.1 MB** —— 34.7 KB/连接被报成 **2 KB/连接**，`fanOutMax` 同时被抬到 351 ms。
那条样本自己把证据写在字段里：`liveSessions:100000 / disconnects:0 / openFds 100013 → 13`。

同一判据的另一面更安静：**15 个 run 的 hold 读数取自"服务端已经掉完连接"的样本**
（`netty-100000` 报 `liveSessions=669`、`p12-webflux-ws` 报 527、`p9-ws-text` 报 7697/20000）。
RSS 几乎没动（连接走了 JVM 的 RSS 不掉），所以**错的是"服务端当时持有多少连接"这个数**，
不是内存 —— 单看 RSS 表看不出任何异常。

⚠ **没有用 `openFds` 当判据**，尽管它看着更好（内核给的，不会滞后）。HTTP/2 下一条 TCP 连接承载多条流：
`p8-sse-h2-20000` 峰期 **20,000 条流只有 242 个 FD** —— 它数的是 socket，不是用户，
会把每一条 h2 run 都选到又早又低的样本上（2746 → 1887 MB）。

**已修**：判据集中到 `bench/final_sample.py`，两道闸都取自序列自身，不引入绝对常数：

| 闸 | 判据 | 为什么是这个数 |
|---|---|---|
| 人口 | `liveSessions ≥ 自身峰值 × 99%` | 10 万条里掉 1 条是 0.001%，这个带宽吸收 harness 自己关慢消费者的动作，又不放过真正掉了人口的尾巴。峰值取自序列而非 `CONNS`：撞 Tomcat 8192 墙的 run 仍然是它自己的有效 run |
| 物理 | 从尾部往回退，凡 RSS 低于平台中位数一半者不认 | 同样的人口下内存掉一半，只能是拆连接，不可能是 hold |

0.5 是标定出来的，不是拍的：全库 52 条序列里假样本落在自身平台的 **0.07×**，
合法样本的最低值是 **0.72×**（`netty-100000` 确实在 hold 内掉了 28% RSS，而连接还留着 99,624/100,000）。
`(0.07, 0.72]` 里任何值都能分开两侧；取 0.5 是假样本侧留 7 倍、合法侧留 1.4 倍。
**收紧到中位数那一档就会误删真样本**，连带丢掉它们身上那些单调累计的计数器（`fanOutMax` 会凭空变小）。

`run.sh`、`collect.py`、`report.sh` 现在共用这一个实现（`report.sh` 此前直接读 `summary.json`
的 `.server`，所以判据修完它仍会打出 2 KB/连接那一行）—— 缺陷 5 的根子正是两处各写了一份规则。

⚠ **第三个消费者是后来才撞出来的**：`ceiling.sh` 末尾那张阶梯汇总表也直接读 `.server`，
所以它同样在判据修好之后继续打出 `p15-rust-100000` 的 **229 MB / 2 KB**。发现过程不是审查，
是本轮改完表格格式后随手跑了一次，看见那行熟悉的数字。判定不受影响（判定从来看不到 RSS），
但那张表是给人念的，每个数字都会被引用。现在它也走 `final_sample.py`，取不到序列才回落 `.server`。
**"同一个规则的第二份拷贝"这件事，数到第三份才数完。**

影响面：52 条序列里 16 条换了样本。除 Rust-100k 那 15 倍之外，RSS 最多动 5.2%；
存活堆只有 5 个 run 动（最大 −5.0%，`p11-h2-spc1-10k`）；`fanOutMax` 动 2 个
（同一条 128.5 → 63.7 ms，那个尖峰本来就来自掉线尾巴，随之丢弃）；
16 个 run 的 `openFds` 反而变准了 —— `p2-tuned-ws-20000` 18110 → 20018，
跟 §2 里"已核实 `openFds` 全部 = 20,018"那句话对上了。

⚠ **旧 run 的 `summary.json` 不回填**（保留当时写了什么，便于回看判据为什么错）。
引用口径是 `results/*/server-samples.jsonl` 时间序列与 `ALL-RUNS.csv`。

### 缺陷 7 · 互斥锁只守了启动窗口
缺陷 1 的锁是 `run.sh` 第 62 行 `mkdir /tmp/ssebench.lock` 拿的，但**放锁的代码在 `cleanup()` 的第一行**，
而 `cleanup` 除了挂在 `trap EXIT` 上，还在**第 82 行被直接调用一次**（开跑前扫尾残留容器）。
于是锁在拿到之后约 20 行就被释放 —— **ramp、90 秒 hold、采样这整段主体是不持锁的**。

发现过程很直接：WS 阶梯跑到最后一档时我去查锁，容器在跑、`run.sh` 有两个活进程、
`/tmp/ssebench.lock` 不存在。

后果就是缺陷 1 描述的那个场景重新打开：两个错开几毫秒以上启动的 run 都能通过守卫，
然后去抢同一批固定容器名。README、PLAN §5、以及本节缺陷 1 的「**已修**」都建立在一个
只有几毫秒有效性的守卫上。**本轮所有数据没有受影响**（阶梯全程只有一个 run 在跑），
但这个保护等于不存在。

**已修**：锁的实现从两个脚本里抽出来，放进 `bench/benchlock.sh`（`run.sh` 与 `profile.sh` 各 source 一次），
`cleanup()` 里不再有 `rmdir`，释放只在 EXIT trap 里发生，且**只有 owner 能释放**。
和缺陷 5/6 同一个道理：规则写两份早晚漂移 —— 两份拷贝当时就已经漂移了（`profile.sh` 的报错文案更短）。
锁目录里写 `pid`，只为把"有人在跑"变成"是这个 pid 在跑"；**死 pid 只报不抢**（pid 会复用，
删掉别人活锁正是这个文件要防的事故）。

四条都在真实 run 上验过，不是只看 `bash -n`：

| 验的东西 | 结果 |
|---|---|
| **run 主体持锁**（就是原来漏掉的那段） | 1,000 连接已建立、`framesWritten` 在涨的 hold 期间，`/tmp/ssebench.lock` 存在且 owner pid 活着 |
| 第二个 run 被挡住 | `bench/run.sh` 打出 `another bench run (pid 23898) holds /tmp/ssebench.lock`、退出码 **3**，且不创建结果目录、不碰任何容器 |
| 崩溃残留 | pid 填 999999 → `looks stale: pid 999999 is not alive — confirm nothing is running, then rmdir it` |
| 非 owner 释放 | 返回码 0、锁**原封不动**（防的是"我死了但别人拿着锁"这种反向事故） |

⚠ 测试里还撞出一个真实脆弱点：`VAR=x . file` 这种前缀赋值在 bash 3.2 里 **source 返回后就被撤掉**，
函数体是之后才执行的，于是读到空 `$LOCK`，报错文案变成 `holds  — refusing to start`（路径是空的）。
路径现在在函数内部解析（`bench_lock_path`），不再依赖 source 时刻的快照。

### 缺陷 8 · PASS/FAIL 分不出「没实现」和「扛不住」
`ceiling.sh` 的判定是一个四条件的 jq 表达式，输出只有 `true|false`。
WS 阶梯里 `rust ws @ 40000` 与 `go ws @ 40000` 打出 `false`，看着像"上限低于 4 万"，
实际是**建连 0 / 40,000、压测端日志 `404 Not Found`、`rejected=20000`、`failed=0`**：
`go-server` 与 `rust-server` 只注册了 `/sse/stream`，`/ws/stream` 只有 JVM 三台实现了。

**容量型失败建连数逼近目标；功能型失败建连数是 0。** 两者在 `true|false` 这一列上完全同形。
这次是我先看到 0 才没写错结论，不是流程拦住的 —— 判据本身没有这个能力。

**已修**：判定行永远带上当初能分开这两者的那几个数 ——
`>>>> netty 40000 : PASS 建连=40000/40000 rejected=0 droppedInHold=0 p99=164ms`；
`established == 0` 单独立一种判定，不再冒充容量结论：
`>>>> rust 1000 : NO CONNECTIONS 建连 0/1000 rejected=1000 — 服务端没有 /ws/stream？这是功能缺失，不是容量结论`。
末尾汇总表的判定列同步认 `NO-ENDPOINT`。

顺带修掉两处同源的静默失败（都是这次实测判定行时撞出来的，不是审查出来的）：

| 撞出来的 | 为什么危险 |
|---|---|
| 阶梯表与判定行的判据**不一致**（表查三条、判定查四条） | 同一档可以上面 `true` 下面 `FAIL`。四条件现在存在一个 `PASS` 变量里，两处共用 —— 又是"规则写两份" |
| jq 里 `[(PRED)\|tostring, .client.x]` | `\|` 是 jq **最低**优先级：布尔值被管道进后面每个元素，报 `Cannot index boolean with string "client"` |

⚠ 那条 jq 错误本身还暴露了第三种静默失败：`read` 拿到 EOF 返回非零，`set -e` 直接让 `ceiling.sh`
**不打一字退出**（第一次跑阶梯验证时两档都是这样消失的）。现在 `read` 失败会打
`VERDICT FAILED — 读不出 <path>` 再退出。**脚本安静地什么都不说，是这套 harness 反复付的同一种学费。**

### 缺陷 9 · 修缺陷 6 的那一行，把整张表截断了 58/64
缺陷 6 给 `report.sh` 补的回落写成了 `def S(k): ... else (.server | n(k)) end`。
`n(x)` 是 `if x == null then 0 else x end`，所以 `.server | n(k)` **把 `k` 本身当值返回** ——
回落分支拿到的是字符串 `"rssMb"`，不是 `.server.rssMb`。正确写法是 `n(.server[k])`。

回落在 `$srv` 里没有这个字段时才走（序列取不到样本，或取到的样本没有该字段）。
全库 64 条里命中两条：`p15-rust-ws-40000` 与 `p15-go-ws-40000` —— 建连 0，
`final_sample.py` 返回空，`.server` 也是 `{}`，也就是缺陷 8 那两条。于是 jq 报
`string ("rssMb") number required` 退出 5。

**真正的代价不是那两行错，是后面所有行都没了。** `report.sh` 开头是 `set -euo pipefail`，
jq 的 stderr 又接了 `2>/dev/null`：`pipefail` 把 jq 的失败传给整条管道 → `set -e` 当场
终止循环 → 排序在那两条之后的**四条 netty WS 阶梯（40k/60k/80k/100k）一并消失**，
末尾那段 RSS 基线说明也没打出来。表只出 58 行，退出码 5，**一个字的报错都没有**。

`RESULTS.md` §9b 的四档数字没有被带错。**这一点可以反推出来，不用靠记忆**：
坏掉的 `report.sh` 从来就没打出过那四行，§9b 的数字只能另有来源；
`ceiling.sh` 的汇总表是唯一另一个产出口，它的同一个回落写成
`($srv.rssMb // .server.rssMb // 0)`，本来就是对的，数字与 §9b 逐档吻合。
**同一个回落，两处各写一份，只有一份写错了** —— 又是缺陷 5/6/7 那个根子。

**已修**：回落改成 `n(.server[k])`；并且行先算好再打，算不出来就打
`<run> ROW FAILED: <jq 报错>` 然后 `continue`，不再终止整张表。
核实：64 条全部出行，标签与磁盘上 64 个 `results/*/summary.json` 逐一对齐，
退出码 0，stderr 空；注入一条坏 `summary.json` 后确认坏行自报、其后的行照常打印。

⚠ 这条是缺陷 8 结尾那句话的第二次学费，而且**就发生在修缺陷 8 的那一轮提交里**：
错的只是一行回落，要命的是它错了以后表选择了沉默。
**验收一张表，要数它有几行，不能只看它打出来的行对不对。**

### 缺陷 10 · 阶梯汇总表不按传输协议过滤，SSE 那张混进了整条 WS 阶梯
`ceiling.sh` 末尾汇总表用一个 glob 选目录，两个分支的口径不对称：

| `MODE` | 旧 `PAT` | glob 选中 | 实际出行 |
|---|---|---|---|
| `ws` | `*p15-*-ws-*` | 6 个 | 6 行，正好是 WS 阶梯 |
| `sse`（默认） | `*p15-*` | 25 个 | **24 行 —— 18 行 SSE 加上那 6 行 WS** |

`*p15-*` 同样匹配 `p15-netty-ws-40000`，**一个 glob 表达不了「p15 但不含 -ws-」**。
（25 与 24 差的那个是一次中断的 run，见本节末。）

⚠ **要害是混了协议，不是行数多。** 这张表一向是累计的 —— 它每次都重扫 `results/` 下所有
`p15-` 目录，不只是本次调用产的，所以"列得比跑得多"本身是它的设计。真正错的是：
问它 SSE，它把 WebSocket 的档位也一起列出来，而这两者的每连接开销相差 63%
（Netty @ 100,000：SSE 40.7 KB vs WS 24.9 KB）—— 混在一张按 `建连/RSS/每连接` 排版的表里读，
很容易把 WS 的便宜记到 SSE 头上。

**没有任何数字被算错**：判定与每一列都来自该行自己的 `summary.json`（`NO-ENDPOINT` 那两行
就是这么来的）。错的是这张表的口径，而这张表每个数字都会被念出来。

**已修**：glob 只回答「哪些 run 带 `p15-` 这个 label」（那正是阶梯自己打的前缀），
传输协议改问 run 自己记下来的 `.mode`，两个分支就对称了，不再依赖命名约定：

```bash
for d in $(ls -d "$HERE"/../results/*p15-* 2>/dev/null | sort); do
  s=$d/summary.json; [ -f "$s" ] || continue
  [ "$(jq -r '.mode // empty' "$s" 2>/dev/null)" = "$MODE" ] || continue
```

核实：`MODE=sse` 出 18 行、WS 行 0 条；`MODE=ws` 出 6 行、SSE 行 0 条。

⚠ 顺带核出 `RESULTS.md` §9 的一处数错：正文写「17 档里 16 PASS、1 FAIL」，

⚠ 另记一条没动的：`results/20260918-004047-p15-rust-80000` 是一次中断的 run，

## 6. 临界点附近方差极大

SSE @ 40,000 同配置两次跑出 **p99 2097 ms（FAIL）** 和 **655 ms（PASS）**，差 3 倍。
崩溃是**阈值效应**（扇出耗时越过 tick 周期），不是渐进退化。

**所以上限应读作区间而非点值**，每档至少重复 3 次。
远离临界点时复现性很好：WS @ 20k 两次独立测得 1175 与 1185 MB，差 0.8%。

## 7. 已知未测

| 未测 | 为什么会改变答案 |
|---|---|
| **TLS** | 真实部署是 HTTPS/WSS；握手 CPU 与每连接 SSL 会话内存不小，且两种 transport 吃的量不同 |
| **网关 / LB** | ALB、Nginx、Envoy 各有连接上限与 idle timeout，通常比应用层先到顶 |
| **重连风暴** | 实例挂掉后的全量重连是最尖的峰值 |
| **Jetty 的容器调优** | Jetty 档排除了 `TomcatTuning`（Tomcat 专有），未测其自身旋钮还能降多少 |
| **Go / Rust 的生产特性** | 两者是最小实现，无鉴权、tracing、优雅停机；给的是**下界**不是承诺 |
| **真机** | 本批跑在单机 OrbStack 容器，按参考项目自身标准不能作为 benchmark of record |
