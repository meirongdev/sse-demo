## 1. 核心结论：容器的选择比 transport 的选择影响更大

**SSE @ 20,000，每客户端一条连接**，`heapLive` 口径：

| 栈 | 每连接（旧二进制） | 当前镜像复核 | Δ |
|---|---|---|---|
| Tomcat（全调优） | 87.6 KB | **无法复核** ⚠ | —— |
| **Jetty**（Spring MVC 不变） | 17.4 KB | **18.3 KB** | +5.3% |
| WebFlux / Netty | 19.4 KB | **19.9 KB** | +2.6% |
| *Tomcat（未调优,§2 的 HTTP/1.1 行）* | *113 KB* | *112.3 KB* | *−0.6%* |

**每连接堆几乎没动（≤5.3%）** —— 活对象图跨二进制是稳的,这是本节最该被引用的部分。

⚠ **Tomcat 那一格复核不了,所以"相对 Tomcat 5.0× / 4.5×"这两个比值现在悬着。**
87.6 KB 出自 `p5c-sse-all2k`、37.9 KB 出自 `p4c-ws-buf-all`,两者都依赖 socket 缓冲与
header size 这些 `summary.json` 没记录的旋钮（METHODOLOGY 缺陷 11）。
用当前镜像**未调优**的 112.3 KB 对 Jetty 的 18.3 KB 是 **6.1×**,但那不是同一个配置,
**不能拿去替换 5.0×**。
同理,**「SSE + Jetty 比 WebSocket + Tomcat 便宜一倍」这句暂时无法核** —— 它的另一半就是 37.9 KB。

⚠ **本节及 §2 / §5 的「每连接」口径 = （`heapLive` − 该栈空载基线）÷ 连接数**，
基线取 `METHODOLOGY.md` §2 记的那一组：**Tomcat 74 MB、Jetty 19 MB、Netty 16.9 MB**。
这组数能把本节两张表的六格逐一复现到 0.1 KB 以内，所以复算任何一格都不用猜：
拿 `ALL-RUNS.csv` 的 `heapLiveMb` 减掉它，再除连接数。
换容器改一行 `pom.xml`，换 transport 要改客户端契约。

### SSE 与 WS 的排序**随容器翻转**

| 每连接 @ 20,000 | SSE | WebSocket | 关系 | 旧二进制的关系 |
|---|---|---|---|---|
| Tomcat（各自全调优） | 87.6 KB ⚠ | 37.9 KB ⚠ | *无法复核* | SSE 贵 2.3× |
| **Jetty** | **18.3 KB** | 19.9 KB | **SSE 便宜 7.8%** | SSE 便宜 17% |
| WebFlux / Netty | 19.9 KB | 13.3 KB | SSE 贵 **1.50×** | SSE 贵 1.9× |

**「SSE 比 WebSocket 开销大」不是 transport 的属性 —— 这条仍然成立。** 在 Netty 上成立，在 Jetty 上不成立，
排序确实随容器翻转。

⚠ **但两个差距都被压缩了一半左右,而且压缩不是来自 SSE。** SSE 侧只动了 +5.3% / +2.6%,
**动的是 WebSocket**:

| | 旧 | 今天 | Δ |
|---|---|---|---|
| **Netty WS** | 10.4 KB | **13.3 KB** | **+27.9%** ← 全表最大单项变化 |
| Jetty WS | 20.9 KB | 19.9 KB | −4.8% |

Netty WS 那 +27.9% 就是比值从 1.9× 掉到 1.50× 的全部原因；Jetty 那两格一升一降,
把 17% 的优势削到 7.8%。**定性结论没变,但"便宜 16–17%"这种量级的说法不能再引用。**

## 3. 崩溃机制：分两个 regime

⚠ **本节两个 regime 都属于旧二进制（§0）,当前镜像上都不复现。** 先看原文:

| SSE @ 40,000 | 缓冲未调 | 缓冲已调 |
|---|---|---|
| 存活堆 | 4494 MB | 3550 MB |
| 堆占用率（上限 5736 MB） | 78% | 62% |
| CPU 中位 | **400%**（钉死） | **133%**（余量 267%） |
| fanOut 峰值 | 2575 ms | 968 ms |

- **regime A（内存压力大）**：GC 并发工作吃满 CPU → 单线程扇出被饿死
- **regime B（压力解除）**：**扇出线程自身吞吐成为上限** —— 一条线程约 4 万次 enqueue/秒，加内存加 CPU 都没用

### 当前镜像上的复核结果

**regime A 在 40,000 档不出现。** 同一个配置、堆只差 0.6%（4466 vs 4494 MB）,但:

| SSE @ 40,000 | 旧二进制 | 当前镜像 |
|---|---|---|
| `fanOutMax` | 2575 ms | **63 ms** |
| p99 | 6291 ms | **262 ms** |
| 服务端 CPU 峰值 | 467% | **307%**（没有钉死） |

整条阶梯（1 万→5 万）`fanOutMax` 从未超过 **112 ms**,服务端 CPU 峰值平稳在 299–326%。

**regime B 的数量级错了 —— 差 11 倍以上。** 5 万档最坏 111.6 ms 内 enqueue 了 50,000 个 session,
即 **≥448,000 次/秒**;而 `fanOutMax` 是最大值,所以这是**下界**。原文写的是 4 万次/秒。

**这也是"改了什么"唯一的行为线索**:旧代码若是**每 session 组一次帧**（每次 enqueue 含一次字符串构建）,
约 4 万/秒正好对得上;`Frame` 现在的 "composed ONCE per room per tick" 就是纯入队,~45 万/秒。
**仍是推断** —— §0 说过,没有重建前的源码可 diff。

⚠ **但机制没有死,只是搬到了 5 万档以上。** 5 万档三次重复里有一次 `fanOutMax` 到了
**560 ms（1 s tick 的 56%）**,见 §2。扇出压力在堆天花板附近确实开始积累,
只是再没越过 tick、也远没到 2575 ms。**「单线程扇出会撞墙」这条结论方向仍在,档位要改。**

### 分片扇出：有效，但只在它该有效的地方

| 对照 | 分片 | fanOut 峰值 | p99 |
|---|---|---|---|
| SSE @ 40,000 | 1 | 469 ms | 655 ms |
| SSE @ 40,000 | 4 | **117 ms** | **459 ms** |
| WS @ 60,000 | 1 | 126 ms | 393 ms |
| WS @ 60,000 | 4 | 148 ms | 393 ms |

SSE 那组 **fanOut 降到 1/4，正好等于分片数**；WS 那组本来就只有 126 ms，扇出不是瓶颈，分片后无变化。
**这个阴性对照比阳性那半更有说服力。**

**判断是否该上分片：看 `fanOutMaxMillis` 是否逼近 tick 周期，不是看连接数。**

## 5. Tomcat 的两类可调项

### WebSocket 每连接缓冲（`WsFrameBase` 构造函数，建连时一次性分配）

| 缓冲 | 默认 | 谁能改 |
|---|---|---|
| `controlBufferBinary` / `Text` | 125 B / 250 B | 固定 |
| `inputBuffer` | 8192 B | 仅系统属性 `org.apache.tomcat.websocket.DEFAULT_BUFFER_SIZE` |
| `messageBufferBinary` | 8192 B | Spring knob |
| `messageBufferText` | 16384 B | Spring knob（**char 翻倍**） |
| **合计** | **33.1 KB** | 调完 5.5 KB |

实测三档（20,000）：默认 78 KB → Spring knob 56 KB → 加系统属性 **37 KB**。
第一步实测省下 **22.0 KB/连接**（1604.8→1175.0 MB / 20,000），字节码算出的是
33.1−11.6 = 21.5 KB，**两者差 2%** —— 同一个量级，不是精确吻合。

### SSE 的三个旋钮

| 配置 | 每连接 | CPU 中位 |
|---|---|---|
| 基线 | 111.8 KB | 57% |
| `max-http-request-header-size` 8→2 KB | 106 KB | 53% |
| 再加两个 NIO socket 缓冲 → 2 KB | **87.6 KB** | **48%** |

⚠ **24.2 KB 里只有 5.8 KB 是 SSE 独得的**；另外 18.4 KB 来自 socket 缓冲，**WebSocket 同样受益**。

## 6. HTTP/2：取决于一个用户开几条流

**20,000 条 SSE 流**：

| 配置 | TCP 连接 | 存活堆 | 每用户 |
|---|---|---|---|
| h2，每连接 1 条流（独立用户） | 20,018 | 3368 MB | **168 KB** |
| h2，每连接 3 条流 | 6,685 | 2001 MB | 98 KB |
| h2，每连接 6 条流 | 3,352 | 1709 MB | 82 KB ⚠ |
| h2，共享 transport（**上界，非流量模型**） | 19 | 1438 MB | 72 KB ⚠ |
| HTTP/1.1 对照 | 20,018 | 2283 MB | 113 KB |

**成本模型**（两点解出，第三点证伪）：

```
h2 每用户 = 99 KB ÷ 每连接流数 + 65 KB
```

跑前落盘预测 spc=3 → **2030 MB**，实测 **2003 MB**，偏差 **−1.3%**。
spc=1@10k 独立验证：预测 164 KB，实测 161 KB。

**盈亏平衡 n ≳ 2.2 条流/连接。** 一个用户 1 条流时 h2 **贵 46%** 且延迟无改善
（10k 干净重测：h2 与 h1.1 的 p99 都是 163.84 ms）。

⚠ **本节两格「每用户」复算不出来，标了 ⚠ 的就是。** 用 §1 记的那个口径
（`heapLive` − 74.5 MB ÷ 连接数，全文其余每一格都能复现）算出来是 **spc6 → 83.7 KB、
共享 transport → 69.8 KB**，表里写的是 82 和 72。这两格不是缺陷 6 造成的过期值 ——
换成修复前的旧堆值（1704.5 / 1448.9 MB）也是 83.5 和 70.4，还是对不上。
**所以是口径不同，不是抄错**，但原文没有记下是哪个口径。

⚠ **模型的两个常数是在缺陷 6 修复前的堆值上解出来的**，本次只刷新了表里的 MB，
没有重新拟合 —— 重拟合是研究判断，不是转录修正。`99 / n + 65` 恰好精确复现
表里的 98（n=3）与 82（n=6），所以它大概率是用上面那两格解的；那两格的口径一旦定下来，
模型常数、`盈亏平衡 n ≳ 2.2`、以及`贵 46%`都要跟着重算。**引用这三个数前先把口径定了。**

**给 SSE 上 HTTP/2 的价值不在内存，是消除浏览器每源 6 连接限制——那是功能问题。**

## 8. 五种运行时（**RSS 口径**）

| SSE @ 20,000 | 空载 RSS | 负载 RSS | 每连接 RSS | p99 | fanOutMax |
|---|---|---|---|---|---|
| Java · Tomcat（全调优） | 294 MB | 3187 MB | **148.1 KB** | 164 ms | 81 ms |
| Java · Jetty | 272 MB | 1523 MB | **64.1 KB** | 164 ms | 62 ms |
| Java · Netty（WebFlux） | 263 MB | 966 MB | **36.0 KB** | 131 ms | 103 ms |
| Go · net/http | **6.6 MB** | 732 MB | **37.1 KB** | 115 ms | 123 ms |
| Rust · axum/tokio | **1.1 MB** | 680 MB | **34.7 KB** | 115 ms | **47 ms** |

**Netty 36.0、Go 37.1、Rust 34.7 —— 相差 7% 以内。** 有 GC 的 JVM、有 GC 的 Go、
无 GC 的 Rust 落在同一量级，说明这 ~35 KB 主要是**每连接 I/O 缓冲，谁都躲不掉**。

**「换 Rust 省内存」在斜率上不成立。** 数量级差距只剩空载基线（263 MB vs 1.1 MB），而它是固定成本：

| 连接数 | JVM 基线折合每连接 |
|---|---|
| 1,000 | 262 KB（压倒性） |
| 10,000 | 26 KB（同量级） |
| 100,000 | 2.6 KB（可忽略） |

**JVM 的问题不是「JVM 重」，是「选了 Tomcat」：148 → 36 KB 是 4 倍，换容器就能拿回；换语言只值 7%。**

不对等声明：Go / Rust 是最小实现（无鉴权、tracing、优雅停机）；Go 的 `chan []byte` 环形缓冲
（256×24 B = 6 KB/连接）比对手贵约 4 KB；Rust 用 axum 而非裸 socket 是刻意的。

## 9. 上限阶梯（每用户一连接，4 vCPU / 8 GB）

`bench/ceiling.sh` 四个运行时：rust / go / netty 各四档，Jetty 从 20,000 起六档。
**18 档里 17 PASS、1 FAIL**（Jetty @ 100,000，见本节末）。判据是 §PLAN 的四条同时满足
（建连 ≥99%、hold 内几乎不掉线、投递率 ≥0.99、p99 <1000 ms）。

| 运行时 | 档位 | 建连 | 投递率 | p99 | RSS | 每连接 | `fanOutMax` | 服务端 CPU |
|---|---|---|---|---|---|---|---|---|

**1. 100,000 对 rust / go / netty 不是上限，只是这台机器测到的最高一档。** 四判据全绿，
最紧的一条（Netty p99 524 ms）离 1000 ms 判据还有一倍，服务端 CPU 最高只用到 264%/400%。
**这三条实测结论只能写成「≥10 万」。** Jetty 是唯一撞判据的，见结论 5。

**2. 每连接 RSS 一路平坦，与 20,000 档的斜率一致。** Rust 34.7 → 34.7 KB（四档方差 0.9%）、
Go 37.1 → 37.5 KB。用 §2 的空载基线单独算斜率也吻合：Rust (3389−1.1) MB / 100,000 = 34.7 KB。

⚠ **Netty 的斜率随规模上升**：20,000 档是 22.5 KB/连接（703−263 MB 的斜率），
100,000 档是 38.0 KB/连接 —— **同一条曲线上的边际成本涨了 69%**，而 Rust / Go 严格线性。
未解释（怀疑 `PooledByteBufAllocator` 的 chunk/arena 随连接数重排），**记为待查，不进结论**。

**3. 先撞的是 tick 预算，不是内存。** 每连接 RSS 在 100,000 档只吃掉 8 GB 的 42–49%，
而 `fanOutMax`（单 tick 扇出全量的最坏耗时，1 s 是 tick 周期）的走势完全不同：

| `fanOutMax` @ 40k → 100k | 增长 | 线性外推到 1 s |
|---|---|---|
| Rust | 36.5 → 66.2 ms（**几乎不随 N 增长**） | 测不到拐点 |
| Go | 165.6 → 416.8 ms | ≈ 24 万（外推） |
| Netty | 141.6 → 381.4 ms | ≈ 26 万（外推） |

这与 §3 的崩溃机制是同一件事：崩溃是**扇出耗时越过 tick 周期的阈值效应**，不是渐进退化。
Rust 的扇出耗时不随 N 增长，是这条阶梯里最值得追的一条线索。**外推列不是实测。**

**4. 内存估算没被打脸，但它确实不是第一道墙。** 按实测每连接 RSS，8 GB 装 ~22 万连接，
100,000 档离它还差一倍，而 CPU/延迟也都没到 —— 三道墙都没碰到，只是**测到这里为止**。

⚠ 每档只跑一次（`ceiling.sh` 的行为）。§6 说过临界点附近同配置 p99 能差 3 倍：
rust / go / netty 距判据有 2–3 倍余量，属「远离临界点时复现性很好」那一侧；
**Jetty 从 80,000 起就贴着判据走，它的档位必须按区间读**（见结论 5）。
**四条曲线的真临界点都仍未测。**

**5. Jetty 撑到 80,000 —— 而"扇出墙与容器无关"这个假设被推翻了。**
文档原先写"扇出代码四条 JVM 路径共用，Jetty 大概率撞同一道墙"。实测不是：

| @ 40,000 | p99 | `fanOutMax` | 失败形态 |
|---|---|---|---|
| Tomcat（§2） | **6291 ms** | 越过 1 s tick（§3） | 30k→40k **悬崖** |
| Jetty（本节） | **262 ms** | 94.0 ms | 164→262→459→655→1049 ms **平滑爬升** |

Jetty 的 100,000 是全部 18 档里唯一把 **4 个 vCPU 真打满**（400%/400%）的一档，
而且只超判据 **4.9%**：p99 1049 vs 1000，建连 99,858/100,000（99.9%）、投递率 0.998、
hold 内掉线 0 —— 另外三条判据都达标。所以它的死因是 **CPU 饱和**，不是扇出 tick
（`fanOutMax` 203 ms 距 1 s 还差 5 倍），也不是内存（6.7 GB / 8 GB 容器的 84%）。

⚠ 判据边缘 + 单档一次 ⇒ 按 §6 自己的教训，**Jetty 的上限写成 8–10 万区间**，
不要写成 80,000 这个点值。它的 p99 在 80k 就只剩 1.5 倍余量（655 vs 1000），
是四条曲线里最早就贴着判据走的。

⚠ **Jetty 的内存口径要单独说。** 它的每连接 RSS 斜率 **≈64 KB**（用 Jetty 空载基线 281 MB 算，
20k/40k/80k 三档分别是 64.2 / 64.4 / 63.9 KB，线性；⚠ 这个 281 MB 与 §8 那张表里
Jetty 的空载 **272 MB** 不一致，两处差 9 MB，折合每连接 0.5 KB —— 斜率的结论不受影响，
但引用空载基线时要注意是哪一个），是四条路径里**最贵**的，比 Netty 的 38 KB 高 69%。
而 §1 / §8 说"Jetty 最便宜"讲的是**存活堆**（17.4–19.4 KB，全场最低）。
**堆便宜、RSS 贵，差 3.4 倍** —— 跨运行时比较必须用 RSS，这条就是最直白的理由；
只比堆会把最费内存的运行时选成最省的。

⚠ **Tomcat 仍然不在这条阶梯上**（`make ceiling` 只列 rust / go / netty，Jetty 是本次手工补的）。
它的 40,000 FAIL 来自 §2 的 SSE 阶梯，没有走过这四条判据的同一套流程。

### 9b. WebSocket 阶梯（`MODE=ws`，判据与上表完全相同）

**只有 Netty 能测。** 四个档位：

| 档位 | 建连 | 投递率 | p99 | RSS | 每连接 | `fanOutMax` | 服务端 CPU |
|---|---|---|---|---|---|---|---|
| 40,000 | 40,000 | 1.000 | 164 ms | 1359 MB | 34.8 KB | 95.5 ms | 261%/400% |
| 60,000 | 60,000 | 1.000 | 262 ms | 1562 MB | 26.7 KB | 121.6 ms | 241% |
| 80,000 | 80,000 | 1.000 | 393 ms | 2049 MB | 26.2 KB | 158.0 ms | 217% |
| **100,000** | 100,000 | 1.000 | **459 ms** | 2433 MB | **24.9 KB** | 199.2 ms | 214% |

`fanOutMax` 四档 95.5 → 199.2 ms，同档 SSE 是 141.6 → 381.4 ms ——
四档分别便宜 **33% / 39% / 50% / 48%**（1.48× / 1.63× / 2.00× / 1.91×）。
**高档位接近一半，低档位没有**，40,000 档只差 1.48 倍。

压测端 CPU 峰值四档 **14–16%/100%**，无一档作废。Netty 的 WS 上限同样是「**≥10 万，未触及**」。

**Go 与 Rust 的 WS 测不出来 —— 服务端根本没实现这个端点。** 两档 `rust ws @ 40,000`、
`go ws @ 40,000` 都是 **建连 0 / 40,000**，压测端日志打的是 **`404 Not Found`**、
`failed=0`，每个压测端 `rejected=20000`（两个压测端，run 级合计 **40,000**）。源码侧对得上：`go-server/main.go` 只注册 `/sse/stream`，
`rust-server/src/main.rs` 是 `Router::new().route("/sse/stream", …)`，`/ws/stream` 只存在于
JVM 三台的 `WsConfig` / `WsHandler` 里。**这是功能缺失，不是容量结论。**
§8 里 Go/Rust 的 WS 那两格一直是「（估）」，真正的原因在这里 —— 不是没人跑过，是跑不通。

⚠ **当时的阶梯分不出这两种失败。** `ceiling.sh` 的判定只有 `true|false` 两个字符，
「服务端返回 404」和「服务端扛不住」打出来一模一样 —— 我差一点就把这次写成
「Go/Rust 的 WS 上限低于 4 万」。看 `established` 与压测端 `rejected` 才分得开：
容量型失败建连数逼近目标，功能型失败建连数是 0。
**这条已经修进脚本**（缺陷 8）：判定行现在永远带 `建连=x/y rejected=… p99=…`，
`established == 0` 单独立成 `NO CONNECTIONS`（汇总表判定列是 `NO-ENDPOINT`），不再冒充容量结论。
上面那两格是修之前跑的，脚本当时只打了个 `false` —— 引用时按「建连 0、404」读，不能按"上限低于 4 万"读。

**换协议在 Netty 上值 40%，不是 7%。** 同为 100,000 连接、同一台机器、同一组判据：

| Netty @ 100,000 | RSS | 存活堆 | `fanOutMax` | p99 | `openFds` |
|---|---|---|---|---|---|
| SSE | 3976 MB | 1956.5 MB | 381.4 ms | 524 ms | 100,022 |
| WS | **2433 MB** | **1287.2 MB** | **199.2 ms** | 459 ms | 100,022 |
| | **−39%** | −34% | **−48%** | −12% | 相同 |

两边 `openFds` 都是 100,022，证明两边都真的承载了 10 万条连接 —— 这个 −39% 不是"负载没打上去"。
用基线 263 MB 算边际：SSE 38.0 KB/连接 vs WS 22.2 KB/连接。

这与 README 结论 2「换协议值 7%」**不矛盾，但把它限定死了**：那个 7% 是 **Tomcat @ 20,000 的存活堆**
（88.3→82.5 KB）。协议收益不是一个常数，它随容器和规模变 —— 在 Netty 的大规模档上，
换协议比"换 JVM 容器"那一步（§8 说只值 7%）值钱得多。**"瓶颈从来不是 transport"这句要按容器分档引用**，
不能当成通用结论往外搬。

## 10. 撞墙顺序（与 transport 无关）

| 墙 | 默认 | 症状 |
|---|---|---|
| Tomcat `maxConnections` | **8192** | **静默**停止 accept：要 12,000 拿到 8,192，`failed=0 rejected=0` |
| WS 每连接缓冲 | 33 KB | 仅 WS |
| accept backlog | 100 | 高速 ramp 被拒 |
| 文件描述符 | 1024 | `Too many open files` |
| 压测端临时端口 | ~28 K | **长得像服务端到顶** |
| 单线程扇出 | — | p99 随连接数跃升（**旧二进制的 Tomcat 实测**；Jetty 同档位不出现，见 §9 结论 5）⚠ |
| **JVM 堆天花板** | `MaxRAMPercentage=70` | **当前镜像上 Tomcat SSE 的第一道墙**：~52,000 连接处 OOM 死亡（§2） |

⚠ **「单线程扇出」这一行在当前镜像上不复现**（§0、§3）：整条 1 万–5 万阶梯 `fanOutMax` ≤112 ms,
先撞到的是上面那道堆墙。**撞墙顺序本身变了 —— 扇出让位给内存。**

## 11. JVM / GC 旋钮（Java 25，当前镜像）

四个 arm 只差 `EXTRA_JAVA_OPTS`，其余旋钮复现 `p2-tuned-sse-40000`。四档全部建连 40,000/40,000、
投递率 ≈1.00、压测端 CPU ≤26.6%，**无一档因压测端饱和作废**（缺陷 4）。
collector 确实换了 —— hold 期间收集次数 G1 72、ZGC 126、Shenandoah 343、G1+COH 69。

| SSE @ 40,000 | heapLive | RSS | 每连接 | `fanOutMax` | p99 | 服务端 CPU |
|---|---|---|---|---|---|---|
| **G1**（默认） | 4469 MB | **5855 MB** | **149.9 KB** | 81.5 ms | **229 ms** | 313% |
| ZGC（分代） | 4884 MB | 6562 MB | 168.0 KB | 91.7 ms | 524 ms | **260%** |
| Shenandoah | **5032 MB** | 6074 MB | 155.5 KB | 35.9 ms | 328 ms | 310% |
| G1 + compact headers | **4386 MB** | **5782 MB** | **148.0 KB** | 80.6 ms | 262 ms | 295% |

**1. 结论：留在 G1，加 `-XX:+UseCompactObjectHeaders`。** 后者在 JDK 25 是 `{product}` 标志
（24 上还要 `UnlockExperimentalVMOptions`），一个 flag 换 **−1.9% 存活堆 / −1.3% RSS**。

⚠ **幅度小是有原因的,不是没生效。** 直接实测 12→8 字节头的收益是**按对象形状变的**:
空对象 16.3→7.9 B、2 个 int 24.3→16.3 B,但 1 个 int / 1 个引用 / `byte[0]` / `byte[8]` **一个字节都不省** ——
4 字节的头缩减只有跨过 8 字节对齐边界时才兑现。**数组在测过的每种形状里都是 0**,
而本负载的每连接成本恰恰是缓冲**载荷**（§4：4 个约 8 KB 的数组就占 32.9 KB）。
所以这个特性对本形状只值个位数百分点。另外 −1.9% 约为 §6 堆复现带（0.8–0.9%）的两倍,
**方向可信、幅度贴着噪声**。

**2. ZGC 在这个形状上是错的选择。** RSS **+12.1%** → 6562 MB / 8192 MB cgroup = **80%**,
吃掉的正是 `Dockerfile` 里 `MaxRAMPercentage=70` 那段注释专门留出的余量,
**而 cgroup 杀进程看的就是 RSS**。换来 CPU 峰值降 17%,在 8 GB 限额下不划算。

**3. `fanOutMax` 那一列不要读。** Shenandoah 的 35.9 ms（−56%）看着最诱人,
但 §6 的补测证明 `fanOutMax` 本身有 **5 倍**的 run 间散布 —— 这个差值落在噪声里,
**重复之前它什么都不说明**。

⚠ **p99 这一列也不是排名。** 229.4 / 262.1 / 327.7 / 524.3 全是直方图桶边界（§3，最坏桶误差 25%），
G1 与 G1+COH 只隔一个桶。

**4. 不值得做的（已判断，未测）**：AOT class loading / method profiling（JEP 483/515）只影响启动，
而测的是 90 s 稳态；structured concurrency、scoped values、stable values 对这个形状没有着力点；
Vector API 没有数值核。**扇出应继续用平台线程** —— `TickPublisher` 的 javadoc 解释了原因：
虚拟线程扇出会和它自己的消费者挤同一批 carrier。

⚠ **这四条 run 的 `EXTRA_JAVA_OPTS` 没有记进 `summary.json`**（缺陷 11），
collector 是从 `gcCount` 反推的。复现这张表要靠外部脚本，不能只靠 `results/`。
